# 투자 업무 AI 에이전트 (캡스톤)

설비투자 업무의 **투자검토 → 투자회의**를 에이전트 2개 + 스킬 1개로 처리한다. 업무 규칙은 이 문서의 「업무 규칙」이 기준이다.
설치·시연은 `README.md`, 역할·권한·안전장치 명세는 `docs/명세.md`.

```
inbox/*.pptx ─▶ [invest-standardize] ─▶ [invest-reviewer] ─▶ out/검토결과.html (설명) ─▶ 검토자 O (엑셀) ─▶ [invest-meeting] ─▶ out/투자회의자료_YYYYMMDD.html
                 다른 양식→표준양식       R-100~R-322          out/검토결과.xlsx (승인)     사람 승인 R-401      M-0~M-9 계획 매칭  표지 + 신청서 원본
```

## 사용 (테스트 방식)
1. 사용자가 `inbox/` 샘플 신청서 한두 개를 일부러 틀리게 고친다 (샘플 초기화는 사용자가 직접: `! python scripts/make_samples.py --force`)
2. "invest-reviewer 로 inbox 신청서 점검해줘" → 원본은 그대로
   - 다른 양식은 invest-standardize 스킬로 표준양식 변환본(out/표준화/) 생성 후 점검 (양식만, 내용 그대로 — 추가·누락 자동 검증)
   - 잘못된 점은 `out/검토결과.html`
3. (필요 시) `out/검토결과.xlsx` ① 상세 검토의 '판단 필요' 행에 검토자 확인 = O 저장
4. "invest-meeting 으로 회의자료 만들어줘" → 회의 상정 건만 받아 회의자료 작성
   - 점검 후 신청서를 고쳤다면 '재점검 필요'로 보류됨 → 2번부터 다시

## 작업 규칙 (Claude·에이전트)
- 원본(`inbox/`, `data/`, `samples/`, `backup_*/`, `표준양식_수정.pptx`, `구현시나리오_보완.xlsx`)은 읽기 전용. 산출물은 `out/` 에만. 훅이 강제한다.
- 사용자가 명시적으로 원본 수정을 요청하면: 먼저 backup_* 에 백업, 훅의 승인 요청을 거친다. 백그라운드 세션처럼 훅이 차단하면 사용자가 터미널에서 직접 실행하도록 명령을 안내한다.
- 스크립트가 확정한 판정은 에이전트가 바꿀 수 없다 (`review.py judge` 가 거부). 에이전트는 AI대기 행만 판단.
- 검토자 확인(O) 은 사람만 표시한다.
- 비밀 값(API 키·토큰·비밀번호)은 저장소 파일에 쓰지 않는다 (훅 차단, `.env` 는 `.gitignore`).
- 테스트: `python -m unittest discover -s tests -v` 또는 `python scripts/selfcheck.py` (한글 깨지면 `PYTHONIOENCODING=utf-8`)
- 패키지: `pip install -r requirements.txt`

# 업무 규칙

## 1. 업무 흐름 (에이전트 적용 전후)

| 단계 | 현재 | 변경 후 |
|---|---|---|
| 투자접수 | 신청자의 투자신청서 내부 결재 후 통보 | 동일 (신청서 pptx 를 `inbox/` 에 접수) |
| 투자검토 | 담당자들이 문서 확인, 검토사항 반영 | 에이전트가 문서 확인 → 검토 필요 사항을 검토자에게 제공 → 반영 |
| 투자회의 | 기존 계획 변경 사항을 반영한 요약장 한 장 + 신청서 자료 세팅 | 요약장(표지)과 자료 준비까지 에이전트가 하고, 회의는 사람이 진행 |

## 2. 투자신청서 표준양식 (칸 구성과 작성 기준)

슬라이드 1 = 메인 표 하나. 왼쪽 칸 이름 / 오른쪽 값.
- **투자명**: 투자 건명 한 줄
- **투자상세**: 아래 상세 표 (머리글 행 + 값 행, 3쌍)

  | 투자시작 | 투자경과 | 투자금액(백만원) | 투자유형 |
  |---|---|---|---|
  | **현수량** | **필요수량** | **투자수량** | **부 유형** |
  | **AREA** | **계획 NO** | **선정 업체** | **견적 수** |

- **투자효과**: 왜 필요한지, 투자하면 무엇이 좋아지는지 서술
- **투자 상세 부가**: 투자유형에 맞는 필수 항목을 `- 항목명` 머리줄 아래에 작성 (§4). 길면 슬라이드를 추가하고 **슬라이드 제목을 항목명과 똑같이** 쓴다.

칸 작성 기준
- 투자유형: 생산필수 / 노후교체 / 생산성 향상(자동화) 중 하나 (주 유형). 부 유형: 두 유형에 걸칠 때만
- 투자시작: 착수 시점 (예: 27.4月) / **투자경과: 투자 시작 후 걸리는 기간(개월 수)** (예: 5개월)
- **현수량 = 지금 가진 수, 필요수량 = 있어야 할 수, 투자수량 = 이번에 살 수**
- AREA: 설치·사용 위치 (경영계획과 다르면 계획 변경으로 표시됨)
- 계획 NO: 경영계획 목록의 번호, 계획에 없으면 "계획外"
- 선정 업체 / 견적 수: 선정한 업체명과 받은 견적 수 (2곳 이상)
- 견적서 비교: 업체마다 `업체: 금액백만원, 설립 YYYY년 (선정)` 형식 또는 표(업체 / 금액(백만원) / 설립연도 / 비고). 최저가가 아니면 `선정 사유:` 문장
- 현 장비 재원 소개: `운용연수: N년`, `보유 수량: N대, 노후 수량: N대, 교체 수량: N대`, 교체 사유
- 글자와 표는 텍스트로 입력 (이미지로 붙인 글자·표는 읽지 못함), 구버전 .ppt 는 .pptx 로

## 3. 검토 규칙

판정 값은 `충족 / 보완 / 판단 필요 / 해당 없음` 4가지. 한 행 = 조건 하나.
종합 상태: 보완 1건 이상 → **보완 요청** / 판단 필요·AI대기 0건 → **검토 통과** / 그 외 → **검토자 확인 필요**.
주체: 스크립트 = `review.py` 가 확정 / AI = 점검 에이전트가 내용을 읽고 판단 / 사람 = 검토자.

보완 요청 문구는 신청자에게 **그대로 보낼 수 있는 한 문장**(…해 주십시오)으로 쓴다. 근거는 **슬라이드 번호 + 원문 인용**.

신생 업체 미선정 사유 예시 문장 (R-106):
> 최저가를 제시한 ○○사(YYYY년 설립, 업력 N년)는 설립 5년이 되지 않은 신생 업체로, 장기 A/S·부품 공급의 지속성과 재무 안정성을 확인하기 어려워 선정에서 제외하였으며, 설치 후 사후 지원까지 안정적으로 받을 수 있는 업력 N년의 △△사를 선정함.

## 5. 경영계획 매칭과 회의 표지 (invest-meeting)

원칙: 신청서의 계획 NO 를 먼저 확인하고, 없거나 맞지 않으면 매칭을 **제안**하고 담당자가 확인한다(표지에 "확인 필요").

| ID | 상황 | 판정 | 표지 비고 |
|---|---|---|---|
| M-0 | 계획 NO 기재 | 기재된 계획과 장비 종류·유형·금액 대조 | 아래 규칙에 따름 |
| M-1 | 장비 종류·위치·수량 모두 같음 | 계획대로 실행 | (공란) |
| M-2 | 장비 종류 같음, 위치(AREA) 다름 | 계획 변경 (위치) | 계획 Z1 → 실행 Z2 로 변경 |
| M-3 | 품목 같음, 수량 다름 | 계획 변경 (수량) | 계획 500대 → 실행 300대로 변경 |
| M-4 | 짝이 되는 계획 없음 (계획外) | 계획 外 | 계획 外 (확인 필요) |
| M-5 | 짝 후보가 2개 이상 | 판단 필요 | 후보 계획 NO 나열 (확인 필요) |
| M-6 | (기집행 +) 실행금액 > 계획금액 | 계획 초과 | 계획 금액 초과 |
| M-7 | 계획 하나를 여러 번 나눠 신청 (집행 이력 있음) | 누적 = 기집행 + 이번 신청 | 누적 350 / 계획 500 (잔여 150) |
| M-8 | 계획은 있으나 이번에 신청 없음 | 미신청 | 표지 하단 '계획 미신청' 목록 |
| M-9 | 계획과 신청의 투자유형이 다름 | 유형 변경 + 판단 필요 (필수 항목은 신청 유형 기준) | 유형 노후교체 → 생산필수 변경 (확인 필요) |

표지 한 장 형식: `No | 투자 심의(투자명) | 유형 | 계획 NO | 경영계획 | 실행금액 | 차이금액 | 비고` + 합계 행.
단위 백만원, 차이 = 실행 − 계획(이번 신청분). 하단에 계획 미신청(M-8). 표지 뒤에 상정 신청서 원본을 순서대로 첨부.
**보류(미상정) 건은 회의자료·브리핑에 넣지 않는다** — 실무자가 확인해 투자신청자에게 전달할 내용이므로 회의자료 에이전트의 최종 보고(실무자용)와 `out/검토결과.html` 로만 전달한다.

## 6. 검토 결과 형식

- 신청서별 상세 (규칙마다 한 행): 신청서 ID / 투자명 / 규칙 ID / 검토 항목 / 판정 / 근거(슬라이드 번호 + 원문 인용) / 보완 요청 문구(보완일 때) / 검토자 확인(O·수정)
- 신청서 요약: 투자명·유형(기재 / 에이전트 판단)·금액 / 충족·보완·판단 필요 건수 / 종합 상태 / 회의 상정(상정·보류)
- 출력: `out/검토결과.html` = 잘못된 점 설명 화면(사람이 읽음), `out/검토결과.xlsx` = 검토자 확인 O 기록(회의자료 에이전트가 읽음)

## 8. 규칙 관리 방법

- **규칙의 기준은 이 문서다.** 에이전트·스킬 문서는 필요한 부분을 같은 문장으로 옮겨 쓰고, `tests/test_rules.py` 가 규칙 행(R-·M-·T)이 이 문서와 같은지, 코드의 규칙 ID 가 빠짐없이 적혀 있는지 확인한다.
- **수치 기준은 `config/기준값.json`** 에 둔다. `[확정 필요]` 는 동료 합의 전 임시값이다. 합의 전 판단이 애매하면 에이전트는 '판단 필요'로 남기고 검토자가 정한다.
- **기준 제공자·이견**: 규칙을 바꿀 때 누가 정했는지(기준 제공자), 사람마다 기준이 다른지(이견)를 아래 변경 이력에 남긴다. 이견이 있는 규칙은 합의 전까지 '판단 필요'로 둔다.
- **바꾸는 순서**: ① 담당자 합의 → ② 이 문서 §3~§7 수정 + 변경 이력 → ③ `config/기준값.json` → ④ `scripts/review.py`(·`match.py`) 와 테스트 → ⑤ 에이전트·스킬 문서의 같은 행 → ⑥ `구현시나리오_보완.xlsx`·`표준양식_수정.pptx` (사용자가 수정) → ⑦ 전체 테스트 통과.
- **정답셋**: 실제 검토 사례가 쌓이면 §5 정답셋과 `tests/` 에 추가한다.
