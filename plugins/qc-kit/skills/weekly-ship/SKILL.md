# /weekly-ship

이번 주 검사기록을 집계 → 감사 → 회의 문장 순서로 출하한다. 기간 인자: `$ARGUMENTS` (없으면 각 에이전트 지침의 기본 기간).

## 공통 규칙
- 모든 산출물은 `out/` 아래. 원본 `*.csv` / `*.xlsx`는 아무 단계에서도 수정하지 않는다.
- 시작 전에 원본 파일의 sha256을 스크래치패드에 저장하고, 끝날 때 다시 비교해 보고한다.
- 서브에이전트는 이름(`qc-kit:qc-aggregator`, `qc-kit:qc-auditor`, `qc-kit:qc-writer`)으로 부른다. 이름이 등록되지 않았다고 나오면 `general-purpose`로 부르고, 프롬프트 첫 줄에 `${CLAUDE_PLUGIN_ROOT}/agents/<이름>.md` 를 Read해서 그 지침을 따르라고 적는다. 이 경우 쓰기 차단 훅이 걸리지 않으니 프롬프트에 쓰기 허용 경로를 명시한다.
- 각 단계의 판정·건수를 `out/ship_log.md`에 한 줄씩 남긴다(단계, 회차, 시각, 결과).
- **감사관이 무엇을 반려했는지는 `out/review.md`에 남긴다.** 오케스트레이터가 감사 회차마다 덧붙여 쓴다(서브에이전트에게 쓰게 하지 않는다). 매 실행 시작 시 새로 만든다.
  - 맨 위: 기간, 실행 시각, 최종 판정, 반려 횟수(0/1/2), writer 실행 여부
  - 회차별 `## 감사 N차`: 판정, **반려 여부와 반려 사유**(반려를 일으킨 항목: 심각도·위치·기대값 vs 실제값·감사 권고), 반려가 아닌 지적(중간/낮음)은 `반려 아님` 표로 따로
  - 반려된 회차 다음에는 `### aggregator 조치`: 항목별로 고침 / 못 고침 / 이견, 그리고 바뀐 수치(전 → 후)
  - 맨 아래 `## 사람이 결정할 것`: 감사의 현업 확인 사항과, 반려가 2회를 넘겨 멈췄다면 남은 문제
  - 출처는 `out/QC_감사.md`(회차별 사본은 `out/rounds/r<N>/QC_감사.md`)의 항목 번호로 단다
- 단계는 순서대로, 앞 단계 보고를 받은 뒤에 다음 단계를 시작한다. 같은 단계를 병렬로 두 번 돌리지 않는다.

## 순서

### 1. 집계 — qc-aggregator
지침대로 `out/통합_검사기록.csv`, `out/정제로그.csv`, `out/집계.xlsx`, `out/QC_요약.md`를 만든다.

### 2. 감사 — qc-auditor
원본에서 독립 재계산해 `out/QC_감사.md`를 만든다. 판정에 따라:

| 감사 결과 | 처리 |
|---|---|
| `통과` | 3단계로 |
| `조건부 통과` (심각도 `높음` 없음) | 3단계로. 조건을 writer에게 그대로 넘긴다 |
| `불통과`, 또는 심각도 `높음`이 1건 이상 | **반려** → 2-1 |

### 2-1. 반려 (최대 2회)
1. 반려 직전 산출물을 `out/rounds/r<회차>/`로 복사해 남긴다 (`QC_감사.md` 포함).
2. qc-aggregator를 다시 부른다. 프롬프트에 `out/QC_감사.md`의 **불일치·문제 목록을 그대로** 넣고, 그 항목만 고치게 한다. 고친 항목마다 무엇을 바꿨는지 `out/QC_요약.md` 끝 `수정 이력`에 적게 한다.
3. qc-auditor를 다시 부른다(처음부터 전체 재감사). 이전 감사 파일은 덮어쓴다.
4. 결과가 다시 반려면 회차를 올려 1로. **반려가 2회 쌓인 뒤 세 번째 감사도 반려면 멈춘다.**
   - qc-writer는 부르지 않는다.
   - 사용자에게 남은 문제 목록(심각도, 위치, 기대값 vs 실제값)과 각 회차 결과를 보고하고, 사람이 판단할 일로 넘긴다.

즉 감사는 최대 3번(최초 + 반려 후 2번), aggregator 재작업은 최대 2번이다.

### 3. 회의 문장 — qc-writer
`out/QC_감사.md`에서 `일치=O`인 수치만으로 `out/QC_회의문장.md`(세 줄, 숫자마다 출처)를 쓴다. 조건부 통과면 그 조건을 프롬프트에 넣는다.

writer 결과는 오케스트레이터가 한 번 확인한다: 줄이 정확히 세 개인지, 문장 속 숫자마다 `[n]` 출처가 있는지, 그 수치가 감사 표에 `일치=O`로 있는지. 어긋나면 writer에게 한 번만 고쳐 달라고 한다(이건 반려 횟수에 넣지 않는다).

### 4. 마무리 보고
- 최종 판정과 반려 횟수(0/1/2), 회차별 감사 결과 한 줄씩
- `out/QC_회의문장.md` 세 줄과 출처 목록 그대로
- 원본 sha256 비교 결과
- 팀 공유 페이지(대시보드)가 있으면, 감사 결과 때문에 바뀌어야 할 수치가 있는지 알리고 갱신할지 **사용자에게 묻는다**. 묻지 않고 갱신하지 않는다.
